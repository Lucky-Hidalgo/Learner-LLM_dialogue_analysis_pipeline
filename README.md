# Learner-LLM dialogue analysis pipeline

Data and analysis code for 

Hidalgo, L., Pérez-Sanagustin, M., Nascimento, A. & Munoz-Gama, J. (2026) *How Does Conversation Unfold? Analyzing Learner–LLM Dialogues Through Multiple Analytical Lenses*. In Interactive Learning Environments. doi: 10.1080/10494820.2026.2739434


159 conversations between 78 students of a second-year Aerospace Science Thermodynamics course and an LLM-based chatbot configured as a Socratic tutor. Every utterance is labelled with three coding schemes by few-shot classification with `gpt-4o-mini`, the labels are turned into an object-centric event log, and the conversations are described at two levels: an aggregate characterisation of the interaction and a cluster-based identification of interaction profiles.

These notebooks are the cleaned-up version of the exploratory analysis: the same code, with the abandoned branches and duplicate versions removed, and one notebook per step of the Methods section. Each notebook says at the top which of the original notebooks it comes from. They are stored with the outputs of the run on the study data, so the results can be read without running anything.

## Contents

```
notebooks/          the analysis, in order (00 -> 11)
coding_schemes/     the three coding schemes: label hierarchy (tags.json) and the classification prompts
data/               the study data (see data/README.md)
data_example/       a small synthetic dataset with the same structure, for trying the pipeline out
requirements.txt    pinned package versions
.env.example        template for the OpenAI key (only needed to run the classification again)
```

## Running it

Notebooks were executed using Python 3.11.

Notebooks `01` and `03` can call the OpenAI API, but both default to `RUN_API = False` and read the
labels obtained in the study, so no key is needed to reproduce the analysis. To classify from scratch,
copy `.env.example` to `.env`, add your key and set `RUN_API = True`. Model output changes over time, so
a new run will not reproduce the stored labels exactly.

`01_few_shot_classification` keeps the workflow as it was run: one coding scheme and one activity at a
time, with the variables to edit at the top. The last section does the same for the whole corpus in one
go, which is what produced the files the rest of the pipeline uses.

## Data

`data/` holds the study data and `data_example/` a synthetic dataset with the same structure and no real
student content, generated by `data_example/make_example_data.py`. Both are documented in
[`data/README.md`](data/README.md).

The conversations are those of the students who consented to the use, the grading and the sharing of
their data. Students appear as pseudonyms (`s108`, ...); no names or e-mail addresses are anywhere in
this repository. The files the original notebooks downloaded from Drive to resolve consent
(`users_emails.csv`, `StudentsIdConsent.xlsx`) are not part of the release; `source/consent.csv`
contains the same flags keyed on the pseudonym.
